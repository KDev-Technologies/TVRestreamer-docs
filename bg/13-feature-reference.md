## 1. Обща картина

### 1.1 Компоненти

| Компонент | Какво прави | Технология |
|---|---|---|
| **tvr-core** | Control plane: REST API, админ панелът, базата, проверката на достъпа за edge, плейлистите, Xtream API, EPG, известията, отчетите. Един core управлява N агента. | Java 21, Spring Boot 4.1, PostgreSQL 16, Redis 7 |
| **tvr-agent** | Data plane: пуска каналите на своя сървър (FFmpeg процеси, TS суичър, анализатор), HTTP-TS relay, RTMP ingest, UDP/SRT/RTMP изходи, DVB тунери, метрики на сървъра. | Java 21 (Spring Boot без уеб сървър), Netty, FFmpeg 7+, TSDuck за DVB |
| **edge (nginx)** | Раздава HLS и HTTP-TS на абонатите. За всеки плейлист пита core (`auth_request` → `/internal/auth`), подписва сегментите (njs) и ги проверява локално. | nginx + njs |
| **tvr-ui** | Админ панелът, BG/EN, светла и тъмна тема. | React, TypeScript, Ant Design |
| **tvr-common** | gRPC договорът агент ↔ core (`agent.proto`). | Protobuf |

### 1.2 Пътят на видеото в един канал

```
източник ──▶ input FFmpeg #1 ──UDP 127.0.0.1──▶ ┐
източник ──▶ input FFmpeg #2 ──UDP 127.0.0.1──▶ ├─ TS суичър (Java, Netty) ──▶ HLS packager FFmpeg ──▶ /live/<slug>/index.m3u8
                                                 │   · анализатор, CC, PCR       │
                                                 │   · избира активния вход      ├─▶ HTTP-TS relay   (/ts/<slug>.ts)
                                                 │   · една времева линия        ├─▶ UDP multicast изход
                                                 └───────────────────────────────┴─▶ SRT / RTMP push (собствен FFmpeg)
```

- Всеки вход има собствен FFmpeg, който само преопакова (`-c copy`, освен при транскодиране) и праща MPEG-TS на loopback UDP порт (диапазон 20000–29999).
- **TS суичърът** приема всички входове, анализира ги и препраща към packager-а само **активния**. Затова смяната на вход не рестартира пакетирането и плейърите не прекъсват (ADR-003).
- Изходите HTTP-TS, UDP и SRT/RTMP се „закачат“ към суичъра (tap) и получават точно това, което получава HLS packager-ът.
- Видеото никога не минава през core. Core изпраща на агента само **желаното състояние** (desired state) и команди.

### 1.3 Връзка core ↔ агент

- Агентът отваря **една** двупосочна gRPC връзка към core и я държи отворена (може да е зад NAT). Първото съобщение е `Hello` (версии, работещи канали, възможности). Core отговаря с `Welcome` (id на сървъра, интервал на heartbeat).
- Агентът праща heartbeat на 5 s, метрики на сървъра на 5 s, статус на каналите при всяка промяна и пълен отчет на 5 s.
- Core праща **DesiredState** — пълен списък с каналите на сървъра и настройките на агента, с растяща версия. Агентът е *reconciler*: пуска липсващото, спира това, което вече не е в списъка, и рестартира канал **само** ако се е променило нещо, което той изпълнява. Промяна от панела се праща веднага; на 30 s има повторно изпращане за всеки случай.
- Команди: рестарт на канал, смяна/закачане на вход, прекъсване на HTTP-TS клиент, лог на канал, рестарт на агента.
- Сървър без heartbeat 15 s е `OFFLINE`.

### 1.4 Роли на сървърите

| Роля | Каналите | Раздаване на зрители |
|---|---|---|
| `ALL_IN_ONE` | да | да |
| `INGEST` | да | не |
| `EDGE` | не | да (има агент заради HTTP-TS relay, метрики и балансиране) |

## 2. Канали

Меню **Потоци → Канали**. Права: четене — всички роли; промени — Admin и Operator (виж §17).

### 2.1 Списък на каналите

- Колони: кадър (thumbnail), име, статус, активен вход (`#1 основен` / `#2 резервен`), битрейт, категория, сървър, **Catch-up** (колко дни архив има в TimeShift), действия.
- Търсене по име, slug или номер (LCN); филтри по статус, категория, сървър, пакет.
- Статусите се обновяват в реално време (SSE, §15), без презареждане.
- Значки за съдържанието: **Черен екран**, **Замръзнал**, **Тишина** (§7.4) и **Резервна картина**, когато е в ефир slate (§4.6).
- Бутон за режима **Винаги включен ⇄ При поискване** направо в реда.
- Групови действия върху избраните канали: **Старт**, **Стоп**, **Премести…** (на друг сървър), **Изтрий…**. При частичен успех се показва колко са готови и първата грешка.

### 2.2 Нов канал / редакция

Формата има четири секции: **Основни**, **Входове**, **Обработка**, **Изходи**.

| Поле | Значение |
|---|---|
| Име | До 120 символа; показва се в плейлистите. |
| Slug | Малки латински букви, цифри и тире, 2–64 символа. Част от адреса за гледане `/live/<slug>/index.m3u8`; трябва да е уникален. |
| Номер (LCN) | 1–9999, по избор; подрежда каналите в плейлистите. Номерът е уникален — формата казва на кой канал вече е. |
| Категория | `group-title` в M3U; по избор. |
| Сървър | Ingest/all-in-one сървърът, на който работи каналът. „Автоматично“ = единственият ingest сървър (при няколко сървъра каналът се закача към сървъра по подразбиране). |
| Режим | **Винаги включен** или **При поискване** (§2.4). |
| EPG ID | XMLTV id на канала (`tvg-id`); празно = slug. |
| Лого | Адрес (`http(s)://`) или качен файл PNG/SVG до 512 KB (§2.6). |
| Включен | Изключен канал не се пуска и не се вижда като работещ. |
| Връщане към основния вход, резервна картина, тригери за failover | §4. |
| Аудио езици, субтитри, транскодиране | §5. |

- **Защита от едновременна редакция:** всеки запис увеличава версията на канала. Ако друг потребител го е променил междувременно, панелът показва „Каналът е променен от друг потребител“ и предлага да се зареди отново (HTTP 409).
- Всички грешни полета се отбелязват наведнъж (сървърът връща списък с грешки по поле).
- Нов канал получава стойностите по подразбиране от **Настройки** (HLS, timeout на входа, failover тригери, връщане към основния, slate, HTTP-TS) — виж §21.
- API: `GET/POST /api/v1/streams`, `GET/PUT/DELETE /api/v1/streams/{id}`.

### 2.3 Действия и статуси

| Действие | Ефект |
|---|---|
| **Старт / Стоп** | Записва `enabled` в базата; агентът пуска или спира процесите. |
| **Рестарт** | Еднократна команда към агента, без промяна в базата. |
| **Смяна на вход / закачане** | §4.5. |
| **Премести** | §13.5. |
| **Изтрий** | Каналът спира и изчезва от списъка, пакетите и плейлистите (меко изтриване — историята в одита остава). Един канал или избрани наведнъж (`POST /api/v1/streams/actions/delete`). |

Статуси, които агентът докладва:

| Статус | Значение |
|---|---|
| `STOPPED` | Каналът е изключен. |
| `STARTING` | Процесите тръгват, още няма данни. |
| `ONLINE` | Активният вход подава данни без проблем. |
| `DEGRADED` | Работи, но с проблем: CC грешки, загубен вход при наличен резервен и т.н. |
| `OFFLINE` | Нито един вход не подава данни (може да е в ефир резервната картина). |
| `ERROR` | Грешна конфигурация или процесът не може да стартира. |

Статусът се пази в Redis с изтичане — агент, който е спрял да докладва, не оставя канал „Онлайн“ завинаги. Всяка смяна на статус се записва и като събитие в историята на канала (§7.6).

### 2.4 Режим „При поискване“ (TVR-063, FR-STR-04)

- Каналът **не работи**, докато никой не го гледа. Първата заявка на зрител за плейлиста го пуска; спира се след **60 s** без зрител (`TVR_ON_DEMAND_IDLE_TIMEOUT`, минимум 20 s).
- Докато каналът тръгва, edge-ът пита origin-а на всеки 500 ms до 6 s. Ако плейлистът още го няма — плейърът получава `503` с `Retry-After` и опитва пак.
- Подходящ за рядко гледани канали: пести CPU, мрежа към доставчика и връзки на доставчика. Неподходящ за канали с UDP/DVB изход или с външни партньори (няма зрители през edge).

### 2.5 Кадър на канала (TVR-064)

На всеки 60 s агентът взима първия кадър от най-новия HLS сегмент и го записва като `thumb.jpg` (ширина 320 px) до плейлиста. Панелът го показва в списъка и в детайла. Няма кадър, когато каналът е спрян, няма видео или тъкмо е тръгнал. Настройки на агента: `tvr.agent.thumbnails.*` (`TVR_AGENT_THUMBNAILS_ENABLED`).

### 2.6 Лога (TVR-047)

- **Качване:** PNG или SVG до 512 KB (`PUT /api/v1/streams/{id}/logo`). SVG файловете се проверяват: SVG със скриптове, обработчици на събития или външни ресурси се отказва.
- Логото се пази в базата по хеш на съдържанието и се сервира на `/logos/{id}.png|svg?v=<хеш>` — промяна на логото сменя адреса, така плейърите не държат старото в кеша.
- Каналът получава новото лого чак при **Запази** на формата.
- В M3U логото е `tvg-logo`.

### 2.7 Категории (TVR-013)

CRUD и подредба (`/api/v1/categories`, `PUT /order`). Категорията е `group-title` в M3U и категория в Xtream API. При импорт липсващите категории се създават автоматично.

### 2.8 Детайл на канала

Табове: **Преглед** (статус, от кога, видео/аудио, последна грешка, плейър в панела, кадър), **Входове** (живото състояние на всеки вход, превключване и закачане), **Изходи** (адресите за гледане), **Анализатор** (§7), **Графики** (24 ч, §7.5), **Събития** (§7.6), **История** (одит на промените по канала, §19), **Лог** (последните редове на FFmpeg и агента, §7.7).

Плейърът в панела ползва временен preview токен на администратора (`GET /api/v1/auth/preview`), не абонатски.

## 3. Входове

Канал има **от 1 до 8 входа** с приоритет (1 = основен). Подреждат се с влачене или стрелки.

### 3.1 Типове и адреси

| Тип | Адрес | Особености |
|---|---|---|
| **HTTP-TS** | `http(s)://…` | MPEG-TS по HTTP. |
| **HLS** | `http(s)://…/index.m3u8` | |
| **UDP / RTP** | `udp://[iface@]239.1.1.1:1234`, `rtp://…` | Multicast или unicast. Локален адрес/интерфейс връзва канала към сървъра (§13.6). |
| **SRT** (TVR-058) | `srt://хост:порт` | `mode`: **caller** (сървърът се свързва към източника) или **listener** (източникът се свързва към `srt://0.0.0.0:порт` — отворете UDP порта). Латентност 20–8000 ms (празно = 120 ms), парола 10–79 символа (AES, `pbkeylen` 16/24/32), stream ID до 512 символа. |
| **RTMP** (TVR-059) | pull: `rtmp(s)://хост/app/stream`; push: `rtmp://0.0.0.0/<app>/<ключ>` | **pull** — сървърът тегли адреса. **push** — енкодер (OBS, vMix, FFmpeg) праща към вградения RTMP ingest на агента на `rtmp://<агент>:1935/<app>` с ключа на потока. Ключът е 8–128 символа; бутон **Нов ключ** генерира случаен. Който знае ключа, може да предава в канала. |
| **RTSP** (TVR-060) | `rtsp://потребител:парола@камера:554/път` | Транспорт TCP (минава през NAT/firewall) или UDP (само в чиста локална мрежа). Звукът по подразбиране се кодира в AAC. |
| **DVB-S/S2** (TVR-105) | `dvb://adapterN[/frontendM]` | Сателитна карта в сървъра на канала (§3.4). |

Позволени са само мрежови протоколи (`http`, `https`, `udp`, `rtp`, `srt`, `rtmp`, `rtmps`, `rtsp`, `dvb`). `file:`, `concat:`, `subfile:` и другите псевдопротоколи на FFmpeg се отказват и от API-то, и от ограничение в базата (SEC-07) — иначе адрес би могъл да чете локални файлове. FFmpeg се стартира винаги със списък аргументи, никога през shell (SEC-06).

### 3.2 Общи опции на вход

| Опция | Значение |
|---|---|
| **Timeout** | 1–120 s (по подразбиране 5). Секунди без данни, след които каналът минава на следващия вход. |
| **Hot standby** | Входът се приема постоянно, дори когато не е активен (§4.2). |
| **Включен** | Изключен вход се прескача. |
| **Програма (PNR)** | За MPTS — кой от програмите да остане (§3.3). |
| **Звук** | `copy` (по подразбиране), `aac` (прекодиране на звука), `none` (без звук). За RTSP по подразбиране `aac`. |
| User-Agent, заглавни редове, повторно свързване, време за анализ | За HTTP/HLS. Ако каналът няма собствена стойност, се взима тази от **Настройки → Входове по подразбиране**. |

При импорт от M3U се пренасят `#EXTVLCOPT:http-user-agent`, `http-referrer` и подобни опции на VLC/Kodi.

### 3.3 MPTS: избор на програма (TVR-061)

Когато източникът носи няколко програми в един поток (MPTS, напр. от multicast на доставчик или сателит), в полето **Програма (PNR)** се задава номерът на програмата (1–65535). В канала остава само тя. Бутонът **Тествай** показва намерените програми в източника с имената им от SDT, за да се избере правилната.

### 3.4 DVB-S/S2 вход (TVR-105, FR-INP-09/10)

- Нужни са: карта в сървъра, TSDuck (`apt install tsduck`), потребителят на агента в група `video`. Каналът трябва да е вързан към сървъра с картата.
- Параметри: стандарт **DVB-S** или **DVB-S2** (по подразбиране), **честота** на транспондера 950–13000 MHz, **поляризация** H/V/L/R, **символна скорост** 1000–45000 kSym/s, **модулация** QPSK (по подразбиране), 8PSK, 16APSK, 32APSK (DVB-S е само QPSK), **FEC** авто или стойност (`3/4`…), **LNB** `universal` (9750/10600, превключване на 11700) или честоти в MHz (`10750` или `9750,10600,11700`), **DiSEqC** порт 1–4.
- **Споделени тунери:** една карта приема един транспондер, а той носи много програми. Всички входове от един транспондер ползват **един** `tsp` процес; агентът разпределя потока към входовете, а всеки взима своята програма с PNR. Вход, който иска друг транспондер на заета карта, чака — няма данни, затова каналът му минава на резервен вход.
- `tsp` се рестартира с backoff, ако спре или не подава данни 5 s (`TVR_AGENT_DVB_RECEIVE_TIMEOUT`).
- DVB входът не може да се тества от панела: пуска се каналът и се гледа логът.

### 3.5 Тест на вход (TVR-022, FR-INP-07)

Бутонът **Тествай** до всеки вход пуска `ffprobe` на core сървъра (до 9 s, най-много 4 едновременно — повече връщат 429). Резултат: контейнер, програми (с имената от SDT), кодеци, резолюция, кадри в секунда, битрейт, езици на аудиото. Грешките са с ясен код: няма отговор навреме, връзката е отказана, няма такъв хост, 404, достъпът е отказан, не е видео поток, няма видео/аудио, протоколът или адресът не е позволен, на сървъра няма ffprobe.

Не могат да се тестват: SRT listener, RTMP push, DVB (източникът идва към сървъра или е хардуер). Тестът е само за Admin и Operator, защото отваря връзка от сървъра. Ако е зададен `TVR_OUTBOUND_DENY` (напр. `private`), тестът не може да стига до изброените мрежи (защита от SSRF; пренасочванията също се проверяват).

API: `POST /api/v1/inputs/probe`.

## 4. Резервиране (failover)

Целият failover се случва в агента, в TS суичъра — без рестарт на пакетирането. Плейърът вижда непрекъснат поток с маркер за смяна (§4.7).

### 4.1 Cold failover (TVR-027, FR-FOV-02)

Обикновен („студен“) вход работи **само докато е активен**. Ако за timeout-а на входа (5 s по подразбиране; плюс 3 s за старт) не пристигне нито една датаграма, агентът пуска следващия вход по приоритет, суичърът минава на него (първо изпраща PAT/PMT, за да разбере packager-ът новите PID-ове), а старият вход се спира. След последния вход идва пак първият — върнал се източник се намира при следващата обиколка.

### 4.2 Hot standby (TVR-051, FR-FOV-03)

Вход с отметка **standby** работи от старта на канала и продължава, дори когато не е в ефир. Суичърът винаги има неговите данни, PAT/PMT и ключови кадри. Когато активният вход замлъкне, каналът не чака целия timeout: след **1 s** тишина (или timeout-а, ако е по-къс) минава на standby входа на следващия ключов кадър — превключването е **под 3 s**. Цена: още една връзка към доставчика и още един FFmpeg за всеки standby вход.

### 4.3 Тригери за качество (TVR-054, FR-FOV-04)

Вход, който подава данни, все пак може да е „счупен“. В **Разширени настройки за failover** на канала:

| Тригер | По подразбиране |
|---|---|
| CC грешки в минута над N (грешките на анализатора + повредените пакети, които FFmpeg вижда в източника) | 0 = изключено |
| Минимален битрейт (kbit/s) | 0 = изключено |
| Превключване при липса на видео (PMT има видео, но пакети не идват) | включено |
| Превключване при липса на аудио | включено |
| Превключване при кодиран (scrambled) поток | включено |
| Задържане — колко дълго трябва да трае проблемът | 5 s (1–300) |

Когато условието трае задържането, каналът минава на standby вход без проблем, иначе на следващия cold вход. Вход, оставен заради качество, не се пробва отново 5 минути. Ако не остане вход — каналът стои където е (записва се в лога веднъж). Стойностите по подразбиране за нови канали са в **Настройки → Превключване**.

### 4.4 Връщане към основния вход (TVR-052, FR-FOV-05)

Докато е в ефир вход с по-нисък приоритет, агентът следи по-високите: standby входовете работят така или иначе, а cold входовете се **пробват** — на всеки 10 s един от тях се пуска до активния. Щом вход с по-висок приоритет е подавал данни без прекъсване **30 s** (настройва се 5–3600 s, „Стабилен за“), каналът се връща на него и се записва събитие `RECOVERED`. Може да се изключи за канала. Вход с проблем в качеството не се брои за стабилен.

### 4.5 Ръчно превключване и закачане (TVR-036, FR-FOV-06)

В таб **Входове** операторът може да превключи на конкретен вход и да го **закачи** (pin). Докато е закачен, автоматичният failover е спрян — входът остава активен дори без данни — до смяна без закачане. Закачането живее, докато работят процесите (рестарт на канала го маха). Колко канала са със закачен вход се вижда и в Prometheus (`tvr_streams_input_pinned`).

API: `POST /api/v1/streams/{id}/actions/switch-input` (`inputId`, `pin`).

### 4.6 Резервна картина (slate) (TVR-099, FR-FOV-08)

Когато **8 s** нищо не е стигнало до packager-а и нито един вход не подава данни, агентът пуска допълнителен FFmpeg с неподвижна картина и текст „Каналът временно не е достъпен“ (текстът се сменя в **Настройки → Превключване**, до 80 символа) и тих звук, в кодеците на канала. Плейърите продължават да играят, вместо да зациклят. Failover-ът продължава зад картината; първият вход, който подаде данни, влиза в ефир на своя ключов кадър и slate-ът спира. Статусът остава `OFFLINE`, а в панела се вижда значка **Резервна картина**. Включва се/изключва се за всеки канал; по подразбиране е включен.

### 4.7 Непрекъсната времева линия и discontinuity (TVR-028, FR-PRC-04)

Всеки входен FFmpeg има собствен часовник, затова при смяна PTS/DTS/PCR биха скочили. Суичърът пуска новия вход на първия му ключов кадър с времена, които продължават тези на стария плюс един сегмент. Packager-ът започва нов сегмент там, а агентът добавя `EXT-X-DISCONTINUITY` пред него в `index.m3u8` — плейърите нулират декодера, ако кодекът, резолюцията или аудиото са различни.

## 5. Обработка на потока

### 5.1 Аудио езици и субтитри (TVR-062, FR-PRC-02)

- **Аудио езици (запази):** ISO 639-2 кодове (`bul`, `eng`…) в реда, в който да излязат — първият е този, с който повечето плейъри започват. Празно = всички пътечки. Пътечка без езиков етикет или без съвпадение отпада. Ако нито една не съвпадне, каналът излиза без звук.
- **Премахни субтитри/teletext:** маха DVB субтитрите и телетекста.
- Важи за всички входове на канала (прилага се от всеки входен FFmpeg), така резервният вход носи същите пътечки.

### 5.2 Транскодиране на видеото (TVR-106, FR-PRC-05, ADR-008)

| Профил | Височина | Битрейт по подразбиране |
|---|---|---|
| Без | — | видеото се копира както идва (без натоварване) |
| 1080p | 1080 | 5000 kb/s |
| 720p | 720 | 3000 kb/s |
| 480p | 480 | 1500 kb/s |

- **Енкодер:** Автоматично (първото налично: NVIDIA NVENC → Intel Quick Sync → процесор), **NVIDIA NVENC** (`h264_nvenc`, нужен `/dev/nvidia0`), **Intel QSV** (`h264_qsv`, нужен `/dev/dri/renderD128`), **Процесор** (`libx264`).
- **Видео битрейт:** празно = този на профила.
- Изходът е H.264. Декодирането, деинтерлейсът (`yadif`, само за кадри, маркирани като interlaced) и мащабирането са на процесора, затова работи с всеки източник (MPEG-2, H.264, HEVC). По-малка картина не се увеличава.
- Ключов кадър на 2 s (на 1 s при нечетна дължина на сегмента), като IDR — сегментите и превключванията започват на ключов кадър.
- Всеки вход кодира, затова и резервният вход дава същия формат. Цена: всеки hot standby вход също заема GPU сесия или процесор.
- Звукът остава според опцията **Звук** на входа; субтитрите се копират.

### 5.3 Име на услугата (SDT)

Полето **Service name (SDT)** е във формата, но **още не се прилага** (TVR-102). Изходите носят името по подразбиране на FFmpeg.

## 6. Изходи

### 6.1 HLS (TVR-019, FR-OUT-01)

- Основният изход за абонатите: `/live/<slug>/index.m3u8`, сервиран от nginx. Сегментите са в работната директория на агента — в продукция tmpfs (`/run/tvr-agent/work`), за да не се износва дискът.
- **Сегмент** 1–30 s (по подразбиране 4), **списък** 2–60 сегмента (6), **праг за изтриване** 1–30 (2). Стойностите по подразбиране за нови канали и бутонът **Приложи за всички канали** са в **Настройки → HLS и HTTP-TS**.
- Агентът чисти на 10 s сегментите, които вече не са в плейлиста (и останалите от предишен packager).

### 6.2 HTTP-TS (TVR-056, FR-OUT-02)

- Relay в агента: `GET /ts/<slug>.ts` праща MPEG-TS на канала (точно каквото получава packager-ът) към всеки клиент, без FFmpeg и без край. За VLC, Smart TV, приемници.
- Нов клиент започва на следващия ключов кадър с последните PAT/PMT — картината е чиста веднага.
- Клиент, който не смогва, губи данни (броят се `bytes_dropped`), но не бави останалите.
- Достъп: зрителят идва през edge (който пита `/internal/auth` само веднъж в началото). Затова агентът докладва отворените връзки на core на всеки 10 s; core проверява достъпа на всяка отново (абонатът може да е спрян или изтекъл) и прекъсва тези, които вече не са разрешени. Това поддържа и сесията на устройството жива.
- Портът на relay-а (8090) трябва да е достъпен само от edge сървърите; без вътрешен токен слуша само на 127.0.0.1.
- Включва се за всеки канал; **Настройки → HTTP-TS изход за нови канали** и бутонът **Включи HTTP-TS на всички канали** (без рестарт на каналите).

### 6.3 UDP multicast / unicast (TVR-057, FR-OUT-03)

- Адрес (IPv4/IPv6 или име), порт, TTL, по избор **локален адрес** и **интерфейс** (напр. `eth1`).
- Изпраща се направо от суичъра на агента (без FFmpeg), в датаграми по 1316 байта (7 TS пакета).
- Локален адрес или интерфейс връзва канала към сървъра (§13.6).

### 6.4 SRT изход (TVR-096, FR-OUT-04)

- **listener:** партньорите теглят `srt://<адрес на агента>:порт` (по един партньор на порт; порт 1024–65535, отворете UDP порта). Връзва канала към сървъра.
- **caller:** агентът праща към `srt://хост:порт` на партньора.
- Латентност (празно = 120 ms), парола, stream ID. Един FFmpeg на изход, захранван от суичъра през loopback.

### 6.5 RTMP push към външна платформа (TVR-096, FR-OUT-05)

Към YouTube, Twitch, Facebook и др.: **адрес на RTMP сървъра** (`rtmp(s)://…/app`) и **ключ на потока**, както ги дава платформата. Видеото се копира; звукът — **както е** или **→ AAC** (повечето платформи искат AAC). Ключът е тайна: шифрован в базата и скрит в одита.

## 7. Анализатор, графики и история

### 7.1 TS анализатор (TVR-026, TVR-053, FR-ANL-01..05)

Агентът анализира в Java всеки работещ вход (по ISO/IEC 13818-1 и ETSI TR 101 290). Таб **Анализатор** показва за активния вход:

- **Общо:** битрейт на целия поток, CC грешки за последните 5 s и от старта, transport грешки, загуби на синхронизация, PSI грешки, **грешки в източника** (повредени пакети, които входният FFmpeg вижда — преопаковането ги скрива от анализатора, затова се броят отделно).
- **Услуги (services):** програмите от PAT с име и доставчик от SDT, тип (TV, радио, H.264 HD…), PMT PID, PCR PID, дали са кодирани (CA дескриптори в PMT или `free_CA_mode` в SDT).
- **PID таблица:** PID, тип (видео/аудио/субтитри/данни/PSI), кодек (`h264`, `hevc`, `aac`, `mp2`, `ac3`…), битрейт, CC грешки (сега и общо), scrambled, език.
- **PCR:** интервал (макс./средно; над 40 ms е нарушение на TR 101 290), jitter на пристигане, отклонение на часовника (ppm, след първите 60 s), прекъсвания.

Данните идват с всеки статус (на 5 s); API: `GET /api/v1/streams/{id}/analyzer`.

### 7.2 Видео/аудио в прегледа

Таб **Преглед** показва кодек, резолюция и битрейт на видеото, кодек и език на аудиото — от анализатора.

### 7.3 Загубени UDP пакети на сървъра (TVR-114)

Процесите на канала говорят по UDP на 127.0.0.1 и искат буфер 4 MB, но Linux тихо реже всяка заявка до `net.core.rmem_max`. Агентът проверява какъв буфер реално са получили сокетите и брои `RcvbufErrors` от `/proc/net/snmp` за последната минута. Ако сървърът губи пакети, страницата **Сървъри** показва „Сървърът губи UDP пакети — картината може да насича“ с командата за поправка. `.deb` пакетът задава sysctl стойностите при инсталация.

### 7.4 Черен екран, замръзнала картина, тишина (TVR-101, FR-ANL-06)

- На всеки 15 s агентът декодира най-новия HLS сегмент на всеки канал: ключовите кадри като малки сиви картини и звука като 8 kHz моно.
- **Черен екран:** пикселите са под яркост 32 (0..255) → докладва се след **15 s**.
- **Замръзнала картина:** кадрите се различават средно по-малко от прага → след **30 s**.
- **Тишина:** звукът е под −60 dBFS → след **30 s**.
- Каналът показва значка, в историята влизат събития `BLACK_DETECTED`, `FREEZE_DETECTED`, `SILENCE_DETECTED`, `CONTENT_RESTORED` (с продължителността), а правилото за известие **Съдържание** може да изпрати известие (§14).
- Настройки на агента: `tvr.agent.content-check.*` (`TVR_AGENT_CONTENT_CHECK_ENABLED`).
- Проблемите със съдържанието **не** предизвикват failover — само известяват.

### 7.5 Графики за 24 ч (TVR-055, FR-ANL-07)

Core събира отчетите на агента (на 5 s) в един ред на минута за всеки канал: битрейт, CC грешки и грешки в източника, най-лошото състояние, активният вход, зрители. Таб **Графики** показва битрейт, CC грешки и зрители за избран период с маркери за смените на вход. Минутните данни се пазят **48 ч**; за отчетите се обобщават на час (§16). API: `GET /api/v1/streams/{id}/metrics`.

### 7.6 Събития на канала (TVR-029, FR-FOV-07)

Всичко, което агентът докладва (`STARTED`, `STOPPED`, `INPUT_LOST`, `INPUT_RESTORED`, `FAILOVER` с от/към и причина, `RECOVERED`, `PROCESS_EXITED` с exit code, `SCRAMBLED_DETECTED`, `CC_ERRORS_HIGH`, `ERROR`, събитията за съдържанието), плюс всяка смяна на статус (`STATUS`). Таб **Събития**, страниране; пазят се **180 дни** в месечни партиции. API: `GET /api/v1/streams/{id}/events`. Таб **История** е одитът на промените по настройките (§19).

### 7.7 Лог на канала (TVR-023, FR-LOG-01)

Последните до 1000 реда (настройва се) на FFmpeg и на агента за канала. Логът живее само в агента; core го иска с команда и чака до 5 s. Логът на спрян канал се пази под slug-а му. Само за Admin и Operator (редовете може да съдържат адреси на входовете). API: `GET /api/v1/streams/{id}/logs?tail=N`.

Меню **Абонати → Абонати**. Права: Admin, Operator — пълни; Support — създава и променя, без изтриване; Viewer — само чете, без токена и линка (§17).

### 8.2 Статуси и действия

| Действие | Ефект |
|---|---|
| **Спри** (`SUSPENDED`) | Гледането спира веднага; **Възстанови** го връща. |
| **Блокирай** (`BANNED`) | Достъпът спира веднага; само администратор може да го възстанови. |
| **Удължи** | С N дни след сегашния последен ден (или след днес, ако е минал) или до конкретна дата; изтекъл абонат става отново активен. Бързи бутони **+N д** в списъка. |
| **Нов токен** | Старият линк спира веднага; абонатът трябва да получи новия. |
| **Изтрий** | Само Admin. |

Всяка промяна на абонат изчиства кеша на достъпа в Redis след записа, така спрян абонат или стар токен спират до секунди, а не след 10 s.

### 8.3 Автоматично изтичане (TVR-046, BR-01)

Всеки ден в 00:00 (Europe/Sofia) активните абонати с минал последен ден стават **Изтекъл** и сесиите им се прекратяват. Изпълнява се и при старт на core (ако е бил спрян в полунощ). Бутонът **Изтичане сега** го пуска ръчно (`POST /api/v1/subscribers/actions/expire`). Дори преди нощната задача проверката за достъп отказва абонат с минал последен ден (`EXPIRED`).

### 8.4 Масово удължаване (TVR-083)

Избрани абонати се удължават наведнъж с N дни или до дата — по същото правило като за един абонат (`POST /api/v1/subscribers/actions/extend`).

### 8.5 CSV импорт и експорт (TVR-083, FR-SUB-07)

- **Експорт** на (филтрирания) списък: потребител, име, телефон, имейл, пакети, устройства, политика, изтичане, IP, държави, бележка, статус, дата на създаване. Паролата е винаги празна; токенът не се изнася.
- **Шаблон** `GET /api/v1/subscribers/import/template.csv`.
- **Импорт:** UTF-8 с или без BOM, разделител `,` или `;`, познати алтернативни заглавия (`user`, `login`, `name`…). Първо **преглед**, който казва какво ще стане с всеки ред (нов, съществуващ, грешка), после импорт на избраните редове.
- Формат на изхода: UTF-8 с BOM (Excel), всяка клетка в кавички, клетка, която започва като формула, получава `'` отпред (защита от CSV injection).

### 8.6 Детайл на абоната

Табове: **Основни**, **Плейлист** (всички линкове за достъп: M3U за HLS и за HTTP-TS, EPG, Xtream данни, HTTP-TS линк за всеки канал; бутони за копиране), **Достъп** (IP, държави, MAC), **Устройства** (§12.3), **История** (одит, §19). Бутон **Сесии** отваря гледащите сега.

## 9. Пакети

Меню **Потоци → Пакети** (TVR-038, FR-PKG-01/02).

- Пакетът е именуван, **подреден** списък канали. Абонатът вижда сбора от каналите на активните си пакети.
- Полета: име, описание, **Активен** (неактивен пакет не дава достъп), **Catch-up** (каналите, които TimeShift записва, получават архив в плейлистите на този пакет — §10.4).
- Каналите се добавят с търсене (отиват в края), подреждат се с влачене и се записват с **Запази реда**. Незаписани промени се пазят от случайно излизане.
- Изтриване на пакет маха само връзките — каналите остават.
- Плейлистите се строят при всяка заявка, затова промяна в пакет важи от следващото опресняване на плейъра.
- API: `/api/v1/packages`, `GET/PUT /api/v1/packages/{id}/streams`.

## 10. Гледане: плейлисти, Xtream, EPG, catch-up

### 10.1 Персонален M3U плейлист (TVR-041, FR-PLY-01/02/05)

- `GET /pl/{token}.m3u?type=hls|ts[&mac=…]` на адреса на edge. Токенът е 32 base62 символа (~190 бита) — не може да се отгатне.
- Разширен M3U, който VLC, TiviMate, Kodi, OTT Navigator четат: `url-tvg`/`x-tvg-url` към EPG-то на абоната, за всеки канал `tvg-id`, `tvg-name`, `tvg-logo`, `tvg-chno` (LCN), `group-title`, при catch-up — `catchup`, `catchup-source`, `catchup-days`.
- `type=hls` — линкове `/live/<slug>/index.m3u8?token=…`; `type=ts` — `/ts/<slug>.ts?token=…` (само каналите с HTTP-TS изход).
- `mac=` се копира във всеки линк (за MAC заключването).
- Линковете сочат **най-малко натоварения edge** (§13.7) и абонатът остава на него, докато той е достъпен и не е пълен.
- Плейлистът се строи от базата при всяка заявка — промяна в пакети, канали или статус важи веднага. Достъпът до самия канал edge-ът проверява отново (§11.1).

### 10.2 Xtream Codes API (TVR-076, FR-AUT-05)

За плейъри, които искат хост, потребител и парола (TiviMate, IPTV Smarters, OTT Navigator…):

- `/player_api.php` (вход, категории, канали), `/get.php` (M3U), `/xmltv.php` (EPG), `/live/{user}/{pass}/{id}.ts|m3u8` и кратките варианти.
- Същите абонат, пакети и канали като плейлиста; каналите имат числови id.
- Паролата е Argon2id (бавна нарочно), а плейърите викат API-то много пъти при старт и при всяка смяна на канал. Затова проверена двойка потребител/парола се помни за кратко (докато паролата не е сменена); грешните пароли се броят по клиент (IPv6 — по /64) и потребител и над лимита заявката се отказва без проверка; от много адреси за един потребител има само забавяне, не заключване — така налучкване от много адреси не заключва собствените устройства на абоната. Едновременните Argon2 проверки са ограничени: при наплив плейърът получава 503 и опитва пак. На edge-а пренасочването на Xtream адресите се кешира по SHA-256 хеш на URL-а, за да не попадат потребител и парола във файловете на кеша.
- Абонат без парола няма Xtream достъп.

### 10.3 EPG (TVR-077, FR-PLY-03)

- В **Настройки → SMTP, Telegram, EPG** се задават един или повече XMLTV източника (обикновени или `.gz`) и интервал на изтегляне (по подразбиране 6 ч; при грешка нов опит след 15 мин).
- Core изтегля източниците (до 120 s и 300 MB всеки), пази само `<channel>` и `<programme>` на каналите на инсталацията (по `tvg-id`/EPG ID), от вчера до 8 дни напред, и пази последното добро копие на диска.
- Всеки абонат получава **собствено** XMLTV само с каналите си: `/pl/{token}.xml` и `xmltv.php`.

### 10.4 Catch-up от TimeShift сървър (TVR-132)

TvRestream няма собствен архив (DVR). Интегрира се с отделен **TimeShift** сървър, който записва канали:

- **Настройки → TimeShift (catch-up):** включено, адрес на API-то на TimeShift, ключ за интеграция, публичен адрес за плейърите, интервал на опресняване (5 мин), вход за Xtream (потребител/парола или токен на плейлиста), „остарява след“ (6 ч, експертна).
- Core чете списъка с канали на TimeShift (`GET {api-url}/api/integration/v1/channels`, с ключа и `If-None-Match`) при старт, на всеки 5 мин и когато TimeShift съобщи за промяна (`POST /api/timeshift/v1/events`). Каналите се съпоставят по `tvrSlug`.
- Плейлистите на пакети с отметка **Catch-up** получават `catchup` атрибутите, вече с данните на абоната. Плейлист никога не чака TimeShift — ползва кеширания списък; последният добър отговор се пази и във файл (`TVR_TIMESHIFT_CACHE_FILE`) и важи 6 ч след последния успешен контакт.
- TimeShift проверява правата на абоната с `GET /api/timeshift/v1/access?token=…` (или `username`/`password`) — същите правила като плейлиста.
- Панелът: колона **Catch-up** в списъка с канали (дни архив / „не се записва“), бутон **Провери връзката** (колко канала, колко с catch-up, колко съпоставени, кои са без поток в TvRestream).

## 11. Защита на гледането

### 11.1 Проверката `/internal/auth` (TVR-042, FR-AUT-01/03)

nginx edge-ът пита core за всеки плейлист (`auth_request`). Core проверява поред:

1. валиден токен →
2. статус (не спрян/блокиран) →
3. последен ден не е минал →
4. каналът е в активен пакет на абоната →
5. IP адресът е в разрешените мрежи →
6. държавата е разрешена (GeoIP) →
7. MAC заключване →
8. лимит на устройствата.

При отказ edge-ът получава причината в `X-Deny-Reason`:

| Причина | HTTP | Кога |
|---|---|---|
| `TOKEN` | 401 | Няма токен, грешен е или е старият след нов токен |
| `EXPIRED` | 403 | Изтекъл или минал последен ден |
| `SUSPENDED` / `BANNED` | 403 | Спрян / блокиран |
| `NOT_IN_PACKAGE` | 403 | Каналът не е в активен пакет, не съществува или е изтрит |
| `IP` | 403 | IP извън разрешените |
| `GEO` | 403 | Държавата не е разрешена или не може да се определи |
| `MAC` | 403 | Абонатът е заключен към MAC, а заявката не носи нито един от тях |
| `LIMIT` | 403 | Ново устройство над лимита или устройство, изгонено от по-ново |

- Правата на токена се кешират в Redis 10 s (**Кеш на проверката за достъп**, 1 s–5 мин); непознат токен също се кешира, така поток от грешни токени не натоварва базата. Edge-ът кешира отговора по хеш на URI, IP, user agent и MAC бисквитката — без токена в кеша.
- Edge-ът и core се разпознават с **вътрешен токен** (`TVR_INTERNAL_TOKEN`, задължителен извън dev); грешен вътрешен токен вдига аларма `TvrPlaybackAuthInternalToken`.
- Ако Redis не работи, гледането се пуска (записва се в лога) — лимитът е бизнес правило и не трябва да спира гледането.

### 11.2 Подписани HLS сегменти (TVR-044, FR-AUT-02, ADR-005)

- Edge-ът (njs) взима плейлиста от origin-а и добавя към всеки сегмент `?s=<подпис>&e=<изтича>&d=<сесия>`. Подписът е HMAC-SHA256 с **ключа за подписване** върху „изтича|slug|сесия“.
- Сегментите се проверяват **локално**, без core: липсващ/фалшив подпис → 403, изтекъл → 410.
- Подписът е за канала и за устройството (сесията), не за един сегмент — URL от сегмент не става за друг канал и след изтичане. Всички копия на препубликуван плейлист се броят към скоростта на сегментите на **едно** устройство (`limit_req`), така един плейлист не може да храни неограничен брой зрители.
- **Валидност на подписа:** 10 s–1 ч (по подразбиране 1 мин).
- **Смяна на ключа** от панела: старият ключ се приема, докато подписите му са валидни, после core го маха — гледащите не прекъсват.

### 11.3 Обвързване на сегментите с IP (TVR-098, FR-AUT-06)

По избор (**Обвързване на сегментите с IP на зрителя**): подписът включва и адреса, от който е взет плейлистът (IPv4 цял, IPv6 — /64 префиксът, защото адресите за поверителност на едно устройство се сменят в него). Копиран URL от друг адрес → 403. URL-ите, подписани преди смяна на настройката, остават валидни до изтичането си. Не е подходящо за абонати, чийто IP се сменя често (мобилни мрежи с CGNAT).

### 11.4 Ограничение по IP и по държава (TVR-097, FR-SUB-06)

- **IP:** списък CIDR мрежи на абоната.
- **Държава:** нужна е MaxMind база (GeoLite2/GeoIP2 Country или City, `.mmdb`, `TVR_GEOIP_DATABASE`). Взима се `country`, иначе `registered_country`. По-нов файл (напр. от `geoipupdate`) се зарежда без рестарт (проверка на 60 s). Без база абонати със зададени държави получават `GEO`.

### 11.5 Заключване към MAC (TVR-104, FR-DEV-02)

Гледат само приемниците с изброените MAC адреси. Приемникът праща MAC-а си като бисквитка `mac` (MAG) или като `&mac=` в линка (Enigma2; плейлистът го копира във всички линкове). Адресите се нормализират до `00:1A:79:AB:CD:EF` независимо как са въведени (`00-1a-79…`, `001A79…`, `001a.79ab.cdef`). Важи и за HTTP-TS връзките. MAC адресът може да се подправи — това е бариера срещу случайно споделяне, не криптографска защита.

## 12. Сесии и устройства

### 12.1 Сесии (TVR-066, FR-SES-01/02/04)

- **Сесия = едно устройство на абоната:** ключът е хеш на абонат + IP + user agent, затова прелистване на канали от същото устройство е същата сесия.
- Устройството е „гледащо“ 30 s след последната заявка, стигнала до core (**Прозорец на сесия**, 10 s–10 мин). С 10-секундния кеш на edge-а гледащо устройство стига до core поне на ~10 s.
- Меню **Абонати → Сесии**: кой гледа сега (абонат, канал(и), IP, устройство, от кога), прекратяване на една сесия или на всички на абоната (Admin и Support). Плейърът спира до ~10 s, устройството се отказва 2 мин (**Блокиране след изритване**).
- **История 90 дни** (`TVR_SESSIONS_RETENTION`), синхронизира се на 10 s.
- API: `GET /api/v1/sessions`, `/sessions/history`, `DELETE /api/v1/sessions/{subscriberId}/{sessionKey}`, `POST /api/v1/subscribers/{id}/actions/kick`.

### 12.2 Лимит на устройствата (TVR-045, TVR-067, BR-06)

- **Откажи новото устройство** (`REJECT_NEW`): ново устройство над лимита получава `LIMIT`.
- **Изгони най-старата сесия** (`KICK_OLDEST`): затваря се сесията, започнала първа, и това устройство се отказва 2 мин — иначе при следващата си заявка би изгонило новото.
- Събитието се праща и като webhook `session.limit_exceeded` (най-много веднъж на 5 мин за абонат).

### 12.3 Устройства (TVR-067, FR-DEV-01)

Картата **Устройства** на абоната показва познатите устройства (user agent, последен IP, първо и последно виждане, дали гледа сега). Изтриване на устройство прекратява и сесията му, ако гледа сега; то се появява отново, когато пусне канал.

## 13. Сървъри и кластер

Меню **Платформа → Сървъри**.

### 13.1 Списък и метрики (TVR-035, FR-NOD-03)

За всеки сървър: роля, статус (Онлайн/Офлайн/Поддръжка), последен сигнал, версии на агента и FFmpeg, CPU, памет, load average (с броя ядра), входящ/изходящ трафик, свободно място в работната директория (tmpfs), брой канали и FFmpeg процеси, загубени UDP пакети. Метриките се пазят в Redis с изтичане — мълчащ агент не показва стари стойности.

### 13.2 Добавяне на сървър (TVR-070, FR-NOD-01, SEC-02)

1. **Добави сървър** създава еднократен ключ, валиден 1 ч, и показва командата за инсталация.
2. На новия сървър `install-agent.sh` (сваля се от core без вход) изтегля `tvr-agent.jar` и CA сертификата, праща ключа с CSR и получава **сертификат на агента**, подписан от частния CA на клъстера (валиден 3 години).
3. Агентът се свързва по **mTLS** на порт 9443. Core приема само текущия сертификат на съществуващ сървър.

Частният CA се създава при първа нужда и се пази в базата, така всички core инстанции го споделят. Сертификатът на mTLS порта може да се подмени без рестарт на core. Алтернатива за прости инсталации: общ токен (`TVR_AGENT_ENROLL_TOKEN`) по обикновения gRPC порт 9090.

### 13.3 Редакция на сървър (TVR-071/072/129)

- **Име** (букви, цифри, `. _ -`).
- **Публичен адрес** — адресът, на който плейърите стигат edge-а (не панела): хост, `хост:порт`, `[ipv6]:порт`, по избор с `https://`.
- **Лимит на изходящия трафик (Mbit/s)** — за балансирането между edge сървърите (§13.7).

### 13.4 Поддръжка (drain) (TVR-071, FR-NOD-04)

- **Ingest сървър:** каналите му се преместват на най-малко натоварените онлайн ingest сървъри (по канали/максимум, после по брой, после по име); на него не се пускат нови.
- **Edge сървър:** спира да получава нови зрители в плейлистите; гледащите сега продължават.
- **Край на поддръжката:** сървърът пак приема канали и зрители. Преместените канали **не** се връщат сами.

### 13.5 Преместване на канали (TVR-071, FR-STR-09)

Избрани канали → **Премести…** → сървър. Каналите спират на сегашния сървър и тръгват на избрания; настройките им не се променят. API: `POST /api/v1/streams/actions/move`.

### 13.6 Автоматично преместване при отпадане на ingest (TVR-100, FR-NOD-05)

- Ако ingest сървър с включени канали е без heartbeat **45 s** (`TVR_CLUSTER_AUTO_MOVE_AFTER`, минимум 20 s), каналите му отиват на най-малко натоварените онлайн ingest сървъри с място. Каналът е пак в ефир около 45 s + няколко секунди след като сървърът е замлъкнал.
- **Не се местят** канали, които работят само на този сървър: RTMP push вход, SRT listener вход или изход, UDP вход/изход с локален адрес или интерфейс, DVB вход. При ръчно преместване и drain се местят — там решава администраторът.
- Сървър, който никога не е бил свързан, не се смята за отпаднал. Веднага след старт на core нищо не се мести 45 s (агентите първо трябва да се свържат).
- Каналите **не се връщат** сами, когато сървърът се върне.
- Каквото не се събере, остава и се пробва пак. Резултатът отива в лога и в webhook `node.channels_moved`. Изключва се с `TVR_CLUSTER_AUTO_MOVE=false`.

### 13.7 Балансиране между edge сървърите (TVR-072, TVR-129, FR-NOD-06)

- Edge-ове са EDGE и ALL_IN_ONE сървърите с публичен адрес, онлайн и не в поддръжка. Без такива линковете ползват **Публичен адрес за абонати** (един сървър).
- Edge с лимит е **пълен**, когато средният му изходящ трафик за 30 s е поне **прага** (по подразбиране 80 %, 10–100) от лимита. Без лимит edge-ът никога не е пълен.
- Нов абонат получава: първо не-пълните, после пълните, после тези без отчет; в групата — най-малкото натоварване, после най-малко абонати, после името.
- **Залепване:** абонатът остава на своя edge, докато той е достъпен и не е пълен; абонатите на пълен edge се преместват със следващото опресняване на плейлиста.
- Когато всеки edge с лимит е над прага една минута, се вдига известие `EDGE_SATURATED` (§14).
- Без Redis изборът е по стабилен хеш на абоната.

### 13.8 Премахване на сървър

Сертификатът се отменя и агентът спира да се свързва (и с общия токен). Сървърът отива в списъка **Премахнати сървъри**; **Разреши отново** го пуска да се запише пак.

### 13.9 Рестарт на агента и на каналите на сървър (TVR-082)

От **Настройки**: **Рестартирай каналите** (на сървъра) и **Рестартирай агента** — агентът спира каналите и излиза с код ≠ 0, systemd го пуска отново.

### 13.10 Защита на сървъра от претоварване (BUG-039)

- FFmpeg процесите тръгват постепенно (ограничение старт/секунда), а не всички наведнъж при старт на агент с много канали.
- Нов FFmpeg не се пуска, ако свободната памет е под прага.
- Всеки FFmpeg получава висок `oom_score_adj`: при липса на памет ядрото убива един FFmpeg (каналът се рестартира), а не агента.
- Правило за известие **Памет на сървъра** (§14).

## 14. Известия и инциденти

### 14.1 Правила (TVR-068, FR-ALR-01)

Меню **Платформа → Известия**. Правилата се проверяват на 5 s.

| Правило | Праг | По подразбиране |
|---|---|---|
| Канал офлайн (`STREAM_OFFLINE`) | секунди в OFFLINE/ERROR | 10 |
| Failover (`STREAM_FAILOVER`) | — (всяка смяна на вход) | |
| CC грешки (`STREAM_CC_ERRORS`) | грешки в минута | 100 |
| Съдържание (`STREAM_CONTENT`) | секунди над изчакването на агента; 0 = веднага | 0 |
| Сървър офлайн (`NODE_OFFLINE`) | секунди без отчет | 30 |
| CPU на сървър (`NODE_CPU`) | % | 90 |
| Мрежа на сървър (`NODE_NIC`) | Mbit/s изходящ | 900 |
| Памет на сървър (`NODE_MEMORY`) | % RAM | 90 |
| Edge-овете са пълни (`EDGE_SATURATED`) | — (прагът е от настройките) | |

Правилото за канали може да следи всички или избрани канали; всяко правило праща до избрани канали за известия или до всички включени.

### 14.2 Канали за известия (FR-ALR-02)

- **Telegram:** токен на бота (от @BotFather; не се показва повече) и chat ID (ботът първо трябва да е добавен в групата).
- **Имейл:** до 20 получателя; SMTP сървърът е в **Настройки → SMTP, Telegram, EPG** (STARTTLS, TLS или без защита).
- **Webhook:** `POST` с JSON `{source, title, text, at}`.
- **Тихи часове** (`HH:mm`–`HH:mm`, в `TVR_ALERTS_ZONE`): тогава до канала не се праща нищо — инцидентите остават в панела.
- Бутон **Тест** за всеки канал. Текстовете на известията са на български.

### 14.3 Инциденти (TVR-069, FR-ALR-03/04)

Меню **Платформа → Инциденти**.

- Първото известие на правило за канал/сървър **отваря инцидент** и се праща.
- Повторенията, докато е отворен, се броят и се пращат **групирани** най-много на 10 мин.
- Условие, което още е налице, се **напомня** на 30 мин, докато не бъде потвърдено.
- Условие, изчезнало за 30 s, **затваря** инцидента със съобщение за възстановяване; failover инцидент се затваря след 10 мин без нов failover.
- **Потвърждаване** (ack) спира групираните съобщения и напомнянията. **Заглушаване** на канал/сървър за период — без известия и без съобщение за възстановяване.
- Затворените инциденти се пазят 90 дни.

## 15. Табло и събития в реално време

### 15.1 Табло (TVR-034, FR-MON-01)

Канали по статус, зрители сега, изходящ трафик на всички сървъри, активни абонати, **канали с проблем**, сървъри (колко онлайн, изход, последен сигнал, версия), последни събития за 24 ч. API: `GET /api/v1/dashboard/summary`.

### 15.2 Събития в реално време (TVR-030, FR-MON-02)

`GET /api/v1/events` (Server-Sent Events) — статус на канали, събития, сървъри. Всяка core инстанция ги получава през Redis pub/sub, така работи и с няколко core. Филтър `?types=stream.status,node.*`. Бавен клиент, изостанал с 1000 събития, се прекъсва; връзката трае най-много 1 ч (или до изтичането на токена). Събитията за сървъри не се показват на Support. Ако връзката падне, панелът показва „Връзката в реално време е прекъсната, свързване…“ и се свързва отново.

## 17. Администратори, роли и вход в панела

### 17.1 Роли (TVR-048, FR-ADM-02)

| | Канали | Абонати | Сървъри | Администратори, API ключове, webhooks, одит, архив, настройки |
|---|---|---|---|---|
| **Admin** | пълни | пълни | пълни | да |
| **Operator** | пълни | четене | четене | не |
| **Support** | четене* | пълни, без изтриване | — | не |
| **Viewer** | четене* | четене** | четене | не |

\* без входовете — адресите им съдържат данните на доставчиците (и без лога на канала). \*\* без токена и линка на абоната — иначе Viewer би гледал като абоната.

Меню **Платформа → Администратори**: създаване, роля, активен, нова парола, изтриване. Администратор не може да смени своята роля, да се деактивира или изтрие, а последният активен Admin не може да бъде премахнат. Промяна на роля, активност или парола отменя refresh токените на потребителя; промяна на роля или деактивиране спира и текущия му access токен още при следващата заявка (токенът се проверява срещу базата) и прекъсва потоците му в реално време.

### 17.2 Вход и сесии (TVR-006, FR-ADM-01)

- Access токен (JWT) за 15 мин (1 мин–1 ч) и refresh токен в httpOnly бисквитка за 7 дни (1 ч–90 дни), с ротация при всяко опресняване. Изтеклите refresh токени се трият всяка нощ.
- Началният администратор се създава от `TVR_ADMIN_EMAIL` / `TVR_ADMIN_PASSWORD`, само ако в базата няма потребители.

### 17.3 Двуфакторен вход (TOTP) (TVR-073, FR-ADM-03)

- Меню на акаунта → **Двуфакторен вход**: QR код за Google Authenticator, Microsoft Authenticator, Authy, 1Password; включва се с първия код. Кодът е 6 цифри на 30 s и се приема една стъпка преди или след.
- За **Admin е задължителен** (`TVR_ADMIN_2FA_REQUIRED`): администратор без 2FA може само да го настрои, преди да ползва нещо друго.

### 17.4 Заключване при грешни опити (FR-ADM-04, BUG-012, BUG-042)

- 5 грешни пароли/кода поред за един имейл **от един адрес** заключват този имейл само за този адрес за 15 мин.
- 50 грешки от всякакви адреси заключват акаунта (тогава само парола + 2FA код).
- 30 грешки от един адрес за всякакви имейли заключват адреса.

## 18. API ключове и webhooks

### 18.1 API ключове (TVR-075, FR-API-02)

Меню **Платформа → API ключове** (само Admin, само от панела). За интеграции: билинг, CRM, скриптове.

- Име, права (scopes), срок. Ключът (`tvr_…`) се показва **веднъж**; пази се само като SHA-256. Може да се отмени по всяко време.
- Заявка: заглавие `X-API-Key: tvr_…`. Грешен, изтекъл или отменен ключ → 401 веднага.
- Права: `streams:read|write`, `packages:read|write`, `subscribers:read|write`, `sessions:read|write`, `nodes:read`, `alerts:read|write`, `audit:read`. `:write` включва `:read`. Ключ никога не може да управлява администратори, ключове, webhooks, настройки или архива.
- Ключът няма роля: входовете на каналите вижда само със `streams:write`, токена на абонатите — със `subscribers:write`.

### 18.2 Webhooks (TVR-095, FR-API-04)

Меню **Платформа → Webhooks** (само Admin).

- Адрес и събития: `stream.status_changed`, `stream.failover`, `subscriber.created`, `subscriber.updated`, `subscriber.expired`, `subscriber.deleted`, `session.limit_exceeded`, `node.status_changed`, `node.channels_moved`.
- Всяка доставка е `POST` с `X-TVR-Event`, `X-TVR-Delivery`, `X-TVR-Timestamp` и **`X-TVR-Signature: sha256=<hex>`** — HMAC-SHA256 на суровото тяло с тайната на webhook-а. Тайната се генерира от core, показва се веднъж и се сменя с **Нова тайна**.
- Получателят трябва да отговори 2xx до 5 s. Иначе нови опити след 1 мин, 5 мин, 30 мин, 2 ч, 6 ч; после доставката е `FAILED`.
- Списък с доставките (статус, опити, отговор) и **Изпрати отново**; бутон **Тест**. Доставките се пазят 7 дни.
- Събитията за абонати идват от одита — затова се пращат за всяка промяна, независимо дали е от панела, API ключ, CSV импорт, масово удължаване или нощното изтичане.
- `TVR_OUTBOUND_DENY` важи и за адресите на webhooks.

## 19. Одит лог

Меню **Платформа → Одит лог** (TVR-074, FR-AUD-01/02; само Admin).

- Кой (имейл на администратора или ключа; „системата“ за автоматични действия), какво (обект и действие), кога, от кой IP, с **разлика преди/след** само за променените полета.

- Таб **История** в канала и абоната е одитът на този обект.
- Пази се **1 година** (`TVR_AUDIT_RETENTION`; 0 = завинаги).

## 20. Импорт и архив на конфигурацията

### 20.1 Импорт на канали от M3U (TVR-049, FR-CFG-02)

Меню **Потоци → Импорт**. Адрес (`http(s)`) или файл на плейлиста на доставчика (M3U / M3U Plus): `#EXTINF` с `tvg-*` атрибутите и `group-title`, `#EXTGRP`, HTTP опциите на VLC/Kodi. **Прегледът** казва какво ще стане с всеки канал (нов, резервен вход към съществуващ канал, пропуснат); импортират се избраните. Slug-ът се генерира от името; липсващите категории се създават. Изтеглянето е до 20 MB, само http(s), и минава през защитата срещу SSRF (и при всяко пренасочване).

### 20.2 Импорт от Cesbo Astra (TVR-078, FR-CFG-03)

JSON конфигурацията на Astra (`astra.conf` или експорт от уеб панела ѝ), масивът `make_stream`. Всеки поток става канал: първият четим вход е основен, останалите — резервни по реда си (приоритети 1..8); UDP и HTTP изходите се пренасят. Опциите на Astra след `#` се превеждат, когато има еквивалент (`pnr` → PNR, `ua` → User-Agent и т.н.). Преглед и избор, както при M3U.

### 20.3 Архив: експорт и импорт на цялата конфигурация (TVR-079, FR-CFG-04)

Меню **Платформа → Архив** (само Admin).

- Цялата конфигурация в **един JSON файл**: категории, канали с входове и изходи, пакети, абонати (по избор, с токените и хешовете на паролите), правила и канали за известия, променените настройки (без тайните и без стойностите от env файла) — за съхранение или пренос на друга инсталация.
- Нарочно **не** влизат: администраторите и техните 2FA тайни, API ключовете, сървърите (те се записват отново), сесиите, метриките, одитът и инцидентите. Връзките между редовете са по естествени ключове, затова файлът се импортира и в празна база.
- Файлът е **шифрован с парола** (съдържа данните на доставчиците и, по избор, абонатите).
- Импорт в същата или празна инсталация: редовете се съпоставят по естествен ключ (категория, пакет и канал за известия — по име; канал — по slug; абонат — по потребител); съществуващ ред се пропуска или презаписва по избор.
- Това **не е** backup на базата — за него виж §22.2.

## 21. Настройки и здраве на сървъра

Меню **Платформа → Настройки** (TVR-082; само Admin). Всички параметри на потоците и мрежата — без ръчна редакция на env файла, `application.yml` или sysctl.

### 21.1 Как работят стойностите

- **Приоритет:** променлива в env файла (`deploy/.env` или `/etc/tvrestreamer/tvrestreamer.env`) → стойност за сървъра → глобална стойност от панела → вградена стойност. Стойност от env файла е само за четене в панела („зададено в env файла“) — махнете я оттам, за да се променя от панела.
- За настройките на агента на неговия сървър печели и собствената му `TVR_AGENT_*` променлива.
- Всяка стойност показва **кога влиза в сила**: веднага; при следващ рестарт на канала; изисква рестарт на агента / core / edge; за нови канали.
- Някои стойности се задават **за сървър** (UDP веригата, агентът, повторната връзка).
- Тайните никога не се показват — само „зададено“; бутон **Генерирай** за ключове.
- Всяка промяна влиза в одита. API: `GET /api/v1/settings`, `PUT|DELETE /api/v1/settings/{key}`, `POST /api/v1/settings/{key}/generate`.

### 22.2 Backup на базата (TVR-087)

`scripts/tvr-backup.sh` / `tvr-restore.sh` и systemd таймер `tvr-backup.timer`: `pg_dump`, шифроване с `age`, копие навън (rsync/rclone), тест на възстановяването. Аларми `TvrBackupFailed`, `TvrBackupTooOld`, `TvrBackupOffsiteFailed`.

### 22.3 Начини на инсталация

`.deb` пакет за Ubuntu (един сървър, с edge и съветник за `deploy/.env`), Docker образи и `docker-compose.prod.yml` (TVR-084), Ansible роли за клъстер (TVR-085), `install-agent.sh` за допълнителен сървър (TVR-070).

### 22.4 Тестове под натоварване и хаос (TVR-088/089/090/065)

2 000 виртуални зрители, 24-часов soak тест с 250 канала, хаос тестове за core/edge/ingest и failover — описани в [load-testing.bg.md](https://github.com/kocetod/TVRestreamer/blob/main/guides/load-testing.bg.md).

## 23. Сигурност на данните

- **Шифроване на тайните в базата** (BUG-041, SEC-05): паролите и заглавията на входовете, SRT паролите, ключовете на RTMP потоците, токените на ботовете, тайните на webhooks и др. се пазят с AES-256-GCM и ключа на инсталацията `TVR_DATA_KEY` (64 hex символа или base64 от 32 байта; или файл — Docker secret). **Пазете копие на ключа извън сървъра** — без него тези данни не могат да се прочетат. Стари некриптирани стойности се шифроват при първия старт с ключ.
- **ProductionGuard** (BUG-029, SEC-03): сървър без `SPRING_PROFILES_ACTIVE` се смята за продукция. Извън `dev` core отказва да стартира без `TVR_JWT_SECRET` (≥ 32 символа), `TVR_INTERNAL_TOKEN` и `TVR_DATA_KEY`/`TVR_DATA_KEY_FILE` — грешката е първото и единственото нещо в лога.
- **SSRF:** адресите, които потребител въвежда (тест на вход, M3U импорт, webhooks, webhook канали), минават през `TVR_OUTBOUND_DENY`; пренасочванията се следват ръчно и се проверяват.
- **Одит без тайни**, CSV без формули, лога без скриптове — виж §19, §8.5, §2.6.
